### `patch/mari-unsandboxed-shell`

- **What:** Adds the opt-in env var `MARINARA_MARI_ALLOW_UNSANDBOXED_SHELL` (default `false`) so Professor Mari's `bash` tool can run on platforms with no OS sandbox — notably Android/Termux, which has neither macOS Seatbelt nor Linux bubblewrap, so `bash` otherwise fails closed. The flag only takes effect when no sandbox backend exists (it never downgrades an available Seatbelt/bubblewrap sandbox), and env secrets are still stripped from the child process; only network-deny and workspace-write confinement are dropped. Also makes Mari's sandbox system-prompt line reflect the live status (sandboxed / disabled / unsandboxed).
- **Why forked:** Upstream declined the change as a product decision. Kept locally for single-user, on-device Termux use.
- **Upstream status:** Declined / not merged.
- **Staging rebase note:** the prompt-line commit conflicts with staging's Mari work in `workspace-agent.service.ts` (one bullet). Resolution: keep the `%%MARI_SHELL_SANDBOX_LINE%%` token and mirror staging's current tool list into `mariShellSandboxPromptLine()`. The CHANGELOG hunk was dropped to avoid a conflict on every sync. Since 2.4.3 the shell spawner is the generic `spawnWorkspaceSandboxedProcess({ executable, args })`, so the Termux shell resolution moved up into `spawnWorkspaceSandboxedShell()`; `mari db transform` also consumes the sandbox status, and the patch explicitly excludes the `unsandboxed` backend there so untrusted transform scripts keep requiring a real OS sandbox behind their own `MARI_DB_ALLOW_UNSAFE_TRANSFORMS` gate. On the 2.4.6 sync upstream rewrote the shell runner: commands now spawn `detached` and are killed as a process group (`killSandboxedProcessTree`, #5892), and every run is followed by a sensitive-file scan that reverts and stages unreviewed changes (#5786). The unsandboxed spawn is `detached` as well, so the group kill reaches its grandchildren, and the post-run scan applies to it unchanged. Upstream also added `writableWorkspace` and `allowChildProcesses` options to `spawnWorkspaceSandboxedProcess()`; the unsandboxed backend cannot enforce either, so it refuses a spawn that asks for a read-only workspace or no child processes instead of ignoring the request. Today only `mari db transform` asks, and it already excludes the unsandboxed backend.
- **Staging rebase note (2.5.1, 77ee9026e):** upstream moved the shell runner out of `workspace-agent.service.ts` into `workspace-commands.ts`, so the first commit's output-banner hunk conflicted. Resolution: take upstream's `workspace-agent.service.ts` and put the backend-aware `Sandbox:` banner in `workspace-commands.ts`. The prompt-line commit conflicted again on the system prompt. Resolution as before: upstream's prompt with the bash bullet replaced by the token, and `mariShellSandboxPromptLine()` placed after `MARI_SYSTEM_PROMPT`. Upstream's new `codeCheck` spawn option needs nothing from the unsandboxed backend. Upstream's `mari-guard-sibling-paths` lane pins the banner as `` `Sandbox: ${sandboxed.backend}`` `` and counts two detached spawns, so a third commit builds the unsandboxed banner inside that template literal and raises the count to three.
- **Staging rebase note (2026-10-25, 601fc97ff):** upstream added a "Marinara notices" section to `docs/CONFIGURATION.md` in the same spot as the patch's "Professor Mari shell commands" section. Resolution: keep both, notices first.
- **Touches:** `packages/server/src/config/runtime-config.ts`, `packages/server/src/services/professor-mari/workspace-shell-sandbox.ts`, `packages/server/src/services/professor-mari/workspace-agent.service.ts`, `packages/server/src/services/professor-mari/workspace-commands.ts`, `packages/shared/src/types/professor-mari-workspace.ts`, `packages/server/src/services/mari-db/mari-transform-sandbox.ts`, `scripts/regressions/professor-mari/shell-sandbox.regression.ts`, `scripts/regressions/mari-guard-sibling-paths.regression.ts`, `.env.example`, `docs/CONFIGURATION.md`.

### `patch/fork-upstream-diagnostics`

- **What:** Teaches the build to resolve its _fork base_ — the newest upstream commit the running checkout contains — and reports it wherever version details already appear. `/api/health` gains a `fork` object (`repo`, `branch`, `baseRef`, `baseCommit`, `baseVersion`, `commitsAhead`); the copied support diagnostics gain `Fork` / `Upstream version` / `Upstream build` / `Upstream commit` lines under the existing `Commit` line; the Updates card gains matching `Fork:` and `Upstream base:` rows. The base is found by taking the merge base of `HEAD` against `upstream/staging`, `upstream/main`, `origin/staging`, `origin/main` and keeping whichever leaves the fewest local commits, so a stock `main` checkout is not mistaken for a fork of `staging`. An optional root `fork-base.json` overrides that search (see below). Resolution order is the build-time snapshot in `build-meta.json`, then `MARINARA_FORK_INFO`, then the live checkout, so container and packaged installs keep reporting it without a `.git` directory.
- **Why forked:** A support ticket filed from this fork was indistinguishable from one filed against stock upstream — the version, build, and commit all described our build, with nothing naming the upstream release it was built from. Whoever reads the ticket needs both.
- **Upstream status:** Not submitted. Written to be upstream-offerable — it is generic fork-detection with no reference to this fork, and everything it adds is omitted entirely when the checkout carries no local commits, so stock output is byte-for-byte unchanged. Worth offering if upstream wants it.
- **Pairs with:** `patch/fork-tooling`, which writes the `fork-base.json` stamp onto the integration branch. The two are independent — the patch falls back to the merge-base search when the stamp is absent, and the stamp is inert without the patch.
- **Staging rebase note (2.5.0):** upstream rewrote `packages/server/scripts/write-build-meta.mjs` into exported `writeBuildMeta({ failed })` and `findChangedBuildFile()` functions. The build script calls the first; `run-server.mjs` imports the second at startup to find a damaged build (#6984). Both commits conflicted there. Resolution: take upstream's file and add the patch's `git()` helper, the fork-base resolution, and a `fork` field in the JSON that `writeBuildMeta()` writes. The git calls run only inside `writeBuildMeta()`, so the startup import does not run them.
- **Touches:** `packages/server/src/config/build-info.ts`, `packages/server/scripts/write-build-meta.mjs`, `packages/server/src/app.ts`, `packages/client/src/lib/support-diagnostics.ts`, `packages/client/src/components/panels/SettingsPanel.tsx`, `packages/client/src/localization/locales/en.json`, `scripts/regressions/open-issues.regression.ts`.

### `patch/openrouter-session-id`

- **What:** Sends the chat id as OpenRouter's `session_id` on chat-completions requests. OpenRouter serves a model from many providers, each with its own prompt cache. Without a session id it only sticks a conversation to one provider after it sees a cache hit, so rerolls and new turns land on different providers and miss until one happens to hit. With the session id, a chat's requests go back to the same provider from the first one. Adds `ChatOptions.sessionId`, set to the chat id on the three main generation calls in `generate.routes.ts`, and applied by `OpenAIProvider` only when the endpoint is OpenRouter.
- **Why forked:** GLM 5.2 rerolls in a live roleplay chat sent an identical 50,710-token prompt and got 0, 0 and 1,600 cached tokens before OpenRouter stuck to a provider, then 50,624 on every later reroll.
- **Upstream status:** Not yet submitted (candidate). Self-contained and provider-gated.
- **Validation:** `pnpm check`, `node ./scripts/run-regressions.mjs --filter scripts/regressions/provider-caching.regression.ts` (new case: session id sent on the chat and tool paths for OpenRouter only).
- **Staging rebase note (2.5.1, 77ee9026e):** upstream moved the tool-call loop into `runToolRounds()`, which builds every request from one `requestOptions()` callback, so the old tool-path hunks conflicted. Resolution: take upstream's file and set `sessionId: input.chatId` in two places, `textChatOptions` and the `requestOptions()` passed to `runToolRounds()`. Those two cover every main generation request.
- **Staging rebase note (2026-10-25, 601fc97ff):** upstream's `requestOptions()` for `runToolRounds()` became a block that also resets `replyThinking` per request. Resolution: take upstream's block and add `sessionId: input.chatId` after `openrouterProvider`, as before.

### `patch/request-telemetry`

- **What:** Records telemetry for every LLM request the main generation path makes. `OpenAIProvider` copies the response's `provider`, `id` and `usage.cost`, and the `session_id` it sent, into `LLMUsage`. A wrapper around the main generation provider times each request and hashes its prompt, and the saved message's `extra.generationInfo` gains `upstreamProvider`, `generationId`, `ttftMs`, `sessionId`, `costUsd`, `presetHash` and `promptSections`, each omitted when unknown. They come from the generation's last successful request, except `costUsd`, which is the sum over its requests. Each request is also appended as one JSON line to `<DATA_DIR>/telemetry/requests-YYYYMMDD.jsonl` (UTC day), including failed and aborted ones, with `messageId` and `swipeIndex` filled in once the reply is saved. Rows have `ts`, `chatId`, `messageId`, `swipeIndex`, `kind` (`reply`, `reroll`, `impersonate`, `continue`), `model`, `connectionProvider`, `presetId`, the generationInfo fields above, `promptTokens`, `cachedTokens`, `cacheWriteTokens`, `durationMs`, `finishReason` and `error`; unknown values are `null`. Agent calls are logged from `emitAgentDebug` as `kind: "agent"` rows with `agentType`, `model`, `promptTokens`, `durationMs`, `finishReason` and `error`. Advanced Memory preparation logs a `kind: "memory_recall"` row with `ok`, `durationMs`, `error` and `resultCount` (recalled scenes plus recalled messages); a failed query embedding now adds `query-embedding-timeout` or `query-embedding-failed` to the recall receipt's reasons, which is where `ok: false` comes from when preparation itself succeeds. `GET /api/telemetry/requests?chatId=&since=&limit=` returns `{ rows }`, oldest first, newest last, `limit` defaulting to 500 and capped at 5000.
- **Granularity of `promptSections`:** one entry per message in the prompt handed to the provider, after fitting and post-processing, named `message[i]`. `kind` is `history` for chat-history messages, `tail` for messages after the last history message, and `section` for everything else; `marker` is not used. Preset sections are merged, wrapped, macro-expanded and depth-injected between assembly and send, so a final message cannot be attributed to one section reliably. `hash` is the first 16 hex characters of SHA-256 over the message text, and `chars` its length. `presetHash` covers the preset's wrap format, parameters and variable values, its sections in `sectionOrder` (content, role, enabled state, marker config and injection settings), its groups, and the chat's resolved choice values. It is absent in conversation and game modes, which do not assemble a preset.
- **Why forked:** Prompt-cache misses on OpenRouter could not be traced to a provider, a prompt change, or a preset edit after the fact. The log answers which request went where, what it cost and which part of the prompt changed, without storing prompt text.
- **Upstream status:** Not submitted. Fork-local instrumentation. It writes JSONL files and message extras only, with no new storage table.
- **Validation:** `pnpm check`, `node ./scripts/run-regressions.mjs --filter scripts/regressions/request-telemetry.regression.ts` (OpenRouter metadata on the chat and tool paths, streaming and not, through to the log and the generationInfo summary; a failed request logged with its error; prompt hashes stable and changing only at the edited message). Also the `provider-caching`, `advanced-memory`, `agent-` and `generat` lanes.
- **Staging rebase note (2.5.1, 77ee9026e):** two conflicts in `generate.routes.ts`. Upstream wraps the runtime provider in `fixedTextProvider()` for a defined Game Master intro. Resolution: wrap the runtime provider with `withRequestTelemetry()` first and pass that to `fixedTextProvider()`, so a fixed intro logs no request. Upstream also moved the saved message's extra into `buildGenerationInfoExtra()` (`routes/generate/saved-message-extra.ts`). Resolution: call `requestRecorder.commit()` before it and merge the summary into the returned `generationInfo`, leaving that helper unchanged.
- **Staging rebase note (2026-10-25, 601fc97ff):** only the imports conflicted: upstream stopped importing `mergeModelContextLimit` and `resolveStoredModelContextLimit` from `model-access-policy.js`. Resolution: upstream's import plus the patch's `request-telemetry.js` import.
- **Touches:** `packages/shared/src/types/generation-integration.ts`, `packages/server/src/services/llm/providers/openai.provider.ts`, `packages/server/src/services/telemetry/request-telemetry.ts`, `packages/server/src/routes/telemetry.routes.ts`, `packages/server/src/routes/index.ts`, `packages/server/src/routes/generate.routes.ts`, `packages/server/src/services/agents/agent-executor.ts`, `packages/server/src/services/advanced-memory.ts`, `scripts/regressions/request-telemetry.regression.ts`.

### `patch/openrouter-gemini-cache-breakpoint`

- **What:** With prompt caching on, an OpenRouter request for a Gemini model carries a `cache_control` breakpoint on the text of the message at the connection's caching depth (`cachingAtDepth`, default 5; tool messages and tool-call turns are skipped), instead of the top-level `cache_control` other models get.

### `patch/keeper-review-ui`

- **What:** Replaces the single markdown textarea in the Lorebook Keeper write-approval dialog with a per-entry review. The client loads the current entries of the target lorebook and compares each proposed entry against them: no entry with that name is **new**, current text followed by added text is **appended**, anything else is **replaced**. A count strip totals entries by kind plus locked entries. Replaced entries get a line diff (reworded lines are paired and word-diffed with `diffWords`, unchanged runs fold, removed lines are counted on the collapsed card); appended entries show the end of the current text and the added lines; new entries render as plain text. Each entry has an include checkbox, inline editing (renaming only for new entries), and removable keys for keys the proposal adds. Locked entries are shown but cannot be selected. Closing, Escape, the backdrop, Discard and Regenerate ask before dropping edits. Accept re-serializes the reviewed entries into the existing approval text format, so the commit endpoint and server are unchanged. Summary and character card proposals keep the textarea. UI copy reuses existing upstream strings where one exists.

### `patch/android-remote-server`

- **What:** The Android APK can open a remote Marinara server over HTTPS instead of only `http://127.0.0.1:<port>`. The bootstrap screen gains **Connect to a remote server**: a dialog takes an address, reduces it to a bare `https://host[:port]` origin, and saves it in SharedPreferences. While it is set, the Termux buttons are hidden, `tryConnect` skips Termux detection and the local-secret handshake, and the WebView loads the remote origin, retrying while it is unreachable (Open in browser also works). **Use local server** in the same dialog clears it. The dialog is reachable from inside the app through **Settings > General > App Behavior > Open Android launcher**. Only `https://` is accepted; http, credentials, paths, queries and fragments are rejected. `network_security_config.xml` is unchanged, so cleartext stays limited to localhost/127.0.0.1. `isServerUrl` compares against the configured origin, so the WebView and the native bridge trust only that origin, and other origins still open externally. Certificate errors cancel the load and count as an unreachable server. With no remote address set, the local flow is unchanged.
- **Why forked:** To use the APK as a full-screen client for a Marinara server on another machine, for example one behind `tailscale serve`, with the bridge features (status bar, notifications, file saving) that a browser tab lacks.
- **Upstream status:** Not submitted. Self-contained in the Android wrapper, so it is upstream-offerable.
- **Validation:** `pnpm check`; new `scripts/regressions/android-remote-server.regression.ts` (static: https-only normalizer, remote branch before the local handshake, no secret or `android-auth` use in remote mode, configured-origin trust, no SSL proceed, cleartext list unchanged); `android-local-auth` and `android-file-chooser-camera` lanes; debug APK built with Gradle 9.8.0; the normalizer exercised against sample inputs with plain Java.
- **Touches:** `android/app/src/main/java/com/marinara/engine/MainActivity.java`, `android/README.md`, `scripts/regressions/android-remote-server.regression.ts`.
